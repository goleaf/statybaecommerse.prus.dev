# Backup & Restore Runbook

This runbook documents the end-to-end backup and recovery process for the Statyba e-commerce platform. Use it to coordinate scheduled backups, emergency restores, and operational verification across engineering, DevOps, and support. Keep the file close during incidents—nearly every action and expectation has a corresponding command reference or checklist below.

## Backup Cadence & Coverage

| Asset | Command | Schedule | Notes |
| --- | --- | --- | --- |
| Primary database (PostgreSQL in production, SQLite in lower environments) | `php artisan backups:database` | Nightly at 01:00 EET via Horizon scheduler | Dumps full schema + data, streams directly to the configured object storage disk. | 
| Incremental database binlogs | `php artisan backups:database --mode=binlog` | Every 15 minutes | Captures write-ahead logs so point-in-time recovery can be achieved between nightly full snapshots. |
| Public media (product images, documents) | `php artisan backups:media` | Nightly at 02:00 EET after DB snapshot completes | Uses chunked sync to avoid timeouts; skips derived conversions regenerated by Spatie Media Library. |
| Config & .env snapshots | `php artisan backups:config` | Every Sunday at 03:00 EET | Captures `.env`, `config/`, and Filament navigation exports for compliance. |
| Verification suite | `php artisan backups:verify` | Every Monday at 08:00 EET | Validates checksum manifests, test restores the latest DB dump into a disposable schema, and ensures media indexes match. |

## Retention Policy

- **Daily snapshots:** keep 35 days of database and media backups (`BACKUP_RETENTION_DAYS=35`).
- **Weekly snapshots:** promote every Sunday run to long-term storage for 26 weeks (`BACKUP_WEEKLY_RETENTION=26`).
- **Monthly snapshots:** retain first-of-month backups for 18 months (`BACKUP_MONTHLY_RETENTION=18`).
- **Verification logs:** retain `storage/logs/backup-verify.log` for 90 days to support audits.
- **Binlog archives:** purge incremental archives older than seven days once the corresponding full snapshot falls out of retention.

Automated pruning runs with `php artisan backups:prune` after the nightly media job. Manual pruning uses the same command with a `--dry-run` flag to confirm deletions.

## Storage Locations

Backups write to the disk defined by `BACKUP_STORAGE_DISK` (default `s3`). For S3-compatible stores:

- `BACKUP_S3_BUCKET` – bucket containing the `/statyba/backups` prefix.
- `BACKUP_S3_PREFIX` – optional subdirectory for environment tagging (`prod/`, `staging/`, etc.).
- `BACKUP_S3_REGION` – ensures uploads target the correct region; required when using IAM roles that span regions.
- `BACKUP_ENCRYPTION_KEY` – 32-byte base64 key for at-rest encryption before upload.
- `BACKUP_DATABASE_CONNECTION` – connection name used for snapshotting (defaults to `pgsql`).
- `BACKUP_PRUNE_STRICT` – set to `true` to block pruning whenever storage verification fails.

On-premises or lower environments can set `BACKUP_STORAGE_DISK=local` to target `storage/app/backups` (ensure volume snapshots capture that path).

## Verification Cadence

1. Horizon triggers `php artisan backups:verify` each Monday.
2. The command imports the most recent database dump into a temporary schema, runs smoke migrations, and performs checksum comparison against the manifest.
3. Media verification performs a metadata-only diff (object count + size). Pass/fail results emit `backup.verify.passed`/`backup.verify.failed` events to the monitoring bus.
4. Failures notify the on-call Slack channel defined by `BACKUP_ALERT_SLACK_WEBHOOK` and open a ticket in Jira via the `BACKUP_ALERT_PROJECT_KEY` integration.
5. After any failed verification, run `php artisan backups:verify --scope=full --force` once remediation steps are applied to close the incident.

## Restore Procedure

Follow this order to minimize inconsistencies:

1. **Database restore**
   - Export maintenance banner via Filament to warn operators.
   - Run `php artisan backups:restore --component=database --from="<timestamp>"` (include `--mode=binlog --to="<iso8601>"` when point-in-time recovery is required).
   - Confirm application migrations with `php artisan migrate --force` once restore completes.
2. **Media restore**
   - Run `php artisan backups:restore --component=media --from="<timestamp>" --chunk=500`.
   - Rebuild derived conversions by queueing `php artisan media:regenerate --recent` if media thumbnails appear stale.
3. **Cache bust**
   - Execute the dedicated cache invalidation command `php artisan cache:bust` to flush config, route, view, and Filament caches in one pass.
   - Warm caches using `php artisan cache:warm` (Composer script `cache:warm` runs the same sequence).
4. **Post-restore validation**
   - Trigger `php artisan backups:verify --scope=smoke` to ensure the restore artifacts match expectations.
   - Re-enable maintenance mode banner once smoke checks succeed.

## Known Pitfalls & Mitigations

- **Credential drift:** Rotated IAM keys frequently break uploads. Always update `BACKUP_S3_KEY`/`BACKUP_S3_SECRET` in the secrets manager and redeploy the Horizon workers before re-running jobs.
- **Large media archives:** Restores exceeding 100 GB can trigger timeouts. Use the `--chunk` and `--throttle` flags on `backups:restore` and stage the job during low-traffic windows.
- **Limited disk space:** Local restores require at least 2× the archive size. Verify available space with `df -h /` before starting.
- **Downtime handling:** Database restores place the site in maintenance mode automatically; media restores do not. Coordinate with support to block write operations until both database and media steps finish.
- **Cross-environment confusion:** Always double-check `APP_ENV` and `BACKUP_S3_PREFIX` before running restore commands to avoid contaminating production with staging data.
- **Corrupted binlog chain:** Missing or corrupt incremental files prevent point-in-time restores. Keep `php artisan backups:status --detail` handy to confirm binlog continuity before starting.
- **Stale caches after restore:** Forgetting to run `cache:bust` results in 500 errors due to config mismatches. Always perform cache bust + warm even if Laravel auto-rebuilds caches during deployment.

Ensure these are populated in the environment (or secrets manager) before enabling scheduled jobs.

## Escalation Path for Failures

1. **Initial triage (SRE on-call)**
   - Review the failing command output in Horizon or the job logs under `storage/logs/backups/*.log`.
   - Retry the command with `--retry` if the failure was transient (e.g., `php artisan backups:database --retry`).
2. **Secondary support (Platform team)**
   - If two retries fail, escalate in the `#ops-escalations` Slack channel tagging the platform rotation.
   - Open a Jira SEV-2 ticket using the `BACKUP_ALERT_PROJECT_KEY` template and attach relevant logs.
3. **Vendor escalation**
   - For storage provider outages lasting >60 minutes, contact the cloud vendor using the support plan tied to the IAM account (`BACKUP_VENDOR_SUPPORT_URL`).
   - Update the incident channel every 30 minutes with progress; coordinate with product support for customer communications.
4. **Post-incident**
   - Schedule a post-mortem within 48 hours.
   - Document corrective actions in `docs/runbooks/BACKUP_RESTORE.md` (this file) and update automation scripts as needed.
   - Close the incident in Jira only after a successful `php artisan backups:verify --scope=full` run and status dashboard confirmation.

## Related Artisan Commands

- `php artisan backups:status` – Lists latest backups, retention windows, verifies job freshness, and highlights verification failures. Use the `--detail` flag to include binlog coverage and storage latency.
- `php artisan backups:database` – Forces an immediate database snapshot outside the schedule. Supports `--mode=binlog` for incremental capture and `--retry` for automatic re-attempts.
- `php artisan backups:media` – Syncs media assets into the backup archive. Use `--chunk` to adjust batch size and `--throttle` to limit bandwidth.
- `php artisan backups:config` – Backs up configuration and environment metadata. Accepts `--mask-secrets` to redact sensitive keys in archives.
- `php artisan backups:restore` – Restores database or media artifacts from the archive. Requires `--component=<database|media|config>` and supports `--dry-run` to preview actions.
- `php artisan backups:rehydrate` – Replays configuration snapshots into a target environment without touching the database; useful for staging parity checks.
- `php artisan backups:verify` – Performs checksum verification and smoke-restore validation. Optional `--scope=<smoke|full>` trims runtime when debugging.
- `php artisan backups:prune` – Removes expired backups per retention policy. Pair with `--dry-run` in production to preview deletions.
- `php artisan cache:bust` – Clears all runtime caches after a restore. Automatically rebuilds config, route, view, and Filament caches.

Keep this list synchronized with `php artisan list backups` output whenever new commands ship.
